# 项目初始化 Skill 设计

## 项目目标

创建名为 `initialize-project` 的可复用 Codex Skill，根据目标仓库的实际状态完成项目初始化，而不是原样复制固定模板。

GitHub 仓库同步命名为 `initialize-project`。

仓库根目录本身就是可安装的 Skill 包，`SKILL.md` 和 `agents/openai.yaml` 直接位于仓库根目录，不再增加二级 Skill 目录。

Skill 包保持自包含且无运行时依赖：

- `SKILL.md` 保存核心触发条件、守则和顺序工作流。
- `references/interview-guide.md` 保存自适应访谈清单和阶段确认规则。
- `references/document-contracts.md` 保存 `AGENTS.md`、`design_doc.md` 和阶段资料的内容契约。
- `references/version-control.md` 保存共享与本机私有模式的 Git 行为。
- `agents/openai.yaml` 保存界面名称、简介和默认调用提示。
- 不提供固定模板资产或初始化脚本，避免语言、技术栈和目标平台被静态文件绑定。

## 适用场景

- 空仓库或新项目：建立完整的初始化规则和资料结构。
- 已有代码的项目：执行增量初始化，保留已有规则和项目资产，只补充已确认的缺口。

Skill 只在用户明确要求初始化项目、设置当前仓库或为已有项目补齐初始化资料时触发。缺少 `AGENTS.md` 或 `.init_repo/` 本身不构成触发条件，普通开发任务不得自动进入完整初始化访谈。

## 资料边界

根目录只保留供 Agent 自动发现的 `AGENTS.md`。内部初始化资料统一进入：

```text
.init_repo/
├── design/
├── research/
└── records/
```

- `design/`：项目设计、阶段方案和架构决策。
- `research/`：事实调研、依赖调查和实验结论。
- `records/`：阶段报告、修复记录和验证记录。
- 测试、工具、依赖清单和交付文档属于项目资产，继续遵循目标项目的既有结构。

## 版本控制选择

初始化时询问用户是否共享 `.init_repo/`：

- 选择共享：不添加忽略规则，初始化资料可以提交；空的 `research/` 和 `records/` 使用 `.gitkeep` 固化目录。
- 选择本机私有：不创建 `.gitkeep`；如果目标项目是 Git 仓库，通过 `git rev-parse --git-path info/exclude` 定位仓库本地排除文件，并幂等追加 `/.init_repo/`，不修改项目 `.gitignore`。
- 如果 `.init_repo/` 已经被 Git 跟踪，不能只靠 exclude 取消跟踪；任何索引变更必须另行说明并征得用户同意。

## 初始化会话

1. 先检查仓库、代码、已有规则和文档，能够从环境查明的事实不询问用户。
2. 只询问尚未确定且会影响结果的决策，不重复询问用户已经提供的信息。
3. 每次只问一个问题，并给出推荐答案；询问方式参考 `grill-with-docs`。
4. 至少覆盖项目目标与成功标准、目标用户与核心场景、范围与非目标、技术栈与运行环境、架构与目录边界、测试与验收、版本控制选择以及阶段拆解。
5. 根据目标和依赖关系提出推荐的阶段划分，并和用户确认每个阶段的工作内容。
6. 随着结论确定，持续更新设计资料和领域语言。
7. 汇总项目边界、环境方案、阶段计划和项目级工作约定，等待用户确认。
8. 只有在用户确认汇总后，才创建或修改目标项目文件。

Skill 自身完整实现上述流程，只参考 `grill-with-docs` 的交互原则，不把它或 `domain-modeling` 作为运行时依赖。

## 阶段规划

- 交付阶段必须是可以独立验收的项目增量，不按固定时间周期或零散任务数量机械切分。
- Agent 先提出完整的推荐阶段划分，再逐阶段与用户确认。
- 每个阶段至少记录目标、包含范围、非目标、前置依赖、主要交付物、验收标准和已知风险。
- 阶段顺序必须说明依赖依据；存在可以并行推进的阶段时明确指出。
- `design/design_doc.md` 始终保存完整阶段路线图。
- 只有在阶段即将开始时，才按需创建 `design/stages/<nn>-<slug>.md` 记录详细方案，避免远期方案过早固化。
- 阶段完成后，在 `records/stages/<nn>-<slug>.md` 记录交付范围、验证结果、遗留问题和结论。

## 已有 AGENTS.md 的处理

- 不覆盖已有 `AGENTS.md`。
- 初始化过程中识别出的项目级工作约定，必须先询问用户是否追加。
- 单项功能需求、阶段计划和一次性实现选择不写入 `AGENTS.md`。

## 已有项目资料的处理

- 读取已有 `README.md`、`docs/`、ADR、设计资料和运行说明，并将其作为初始化事实来源。
- 不自动移动、重命名或复制已有资料；仍然有效的权威文档由 `design_doc.md` 直接引用。
- `.init_repo/` 只补充已有资料没有覆盖的项目边界、阶段计划和决策。
- 已有资料之间或已有资料与代码现状冲突时，逐项向用户说明证据并确认当前事实。
- 已有 `.init_repo/design/design_doc.md` 时执行增量更新，不覆盖未经确认的原有内容。

## AGENTS.md 与设计资料的边界

- `.init_repo/design/design_doc.md` 是项目目标、技术选型、版本、选型理由、架构边界、运行环境和阶段路线图的唯一事实来源。
- `AGENTS.md` 只规定 Agent 的工作方式、确认边界和验证义务，不重复记录完整技术选型。
- `AGENTS.md` 必须明确要求 Agent 在架构或技术选型相关工作前阅读 `design_doc.md`，不得未经确认擅自更换已确定的框架、数据库、包管理器或其他关键方案。
- 如果某项技术决定需要强制执行，`AGENTS.md` 只写行为限制并引用设计资料，选择内容和理由仍只保存在 `design_doc.md`。
- 新建 `AGENTS.md` 时写入上述边界；已有 `AGENTS.md` 时，先询问用户是否追加。

## 文档语言

- 访谈和新建文档默认使用用户当前使用的语言。
- 增量更新已有文档时保持该文档的主要语言，不为了统一语言而整体翻译或重写。
- API、命令、文件名、代码标识、模型名、包名和原始报错保留英文原文。

## 执行边界

- 初始化阶段只检查现状、确认方案，并固化项目规则、设计、运行环境方案和阶段计划。
- `design_doc.md` 记录环境名称、关键版本、创建命令、激活方式和依赖管理入口。
- 初始化默认不创建运行环境，不安装、升级、降级或卸载依赖，也不大规模改写锁文件。
- 用户明确要求执行环境搭建时，将其作为单独的交付阶段，在再次确认范围和影响后实施。
